# 多模型协作方法论

## 方法论概述

### 核心理念

通过编排多个 AI 模型协同工作，利用不同模型的差异化能力，得到比单模型更高质量的结论。

**默认双模型：Claude（主，运行本 skill）+ Codex（外部）。** 这是经验上最稳的组合——模型越多，越容易遇到某个 CLI 卡死/超时/鉴权失败，把整个流程拖长。所以默认只编排这两个，保证它们稳定可用即可。需要接入第三个模型时，在 `~/.config/cross-review/models.yaml` 里加一段 `invoke` 模板即可（见 Step 2），但不要为"支持任意多模型"预设复杂机制。

适用于任何需要多视角或交叉验证的任务：方案评审、架构设计、代码审查、技术选型、方向决策、内容创作等。

### 两种模式

| 模式 | 轮次 | 适用场景 |
|------|------|----------|
| 快速模式 | 2 轮 + 轻量对抗 | 相对明确的任务，需要多视角但不需要深度对抗 |
| 完备模式 | 4 轮（含可选 2.5 轮）| 复杂/高风险/高不确定性任务，需要充分交叉验证和对抗性检验 |

**模式选择**：用户明确表达（"完备""充分讨论""深入设计" → 完备；"快速""简单看看""过一下" → 快速）则直接采用；无法判断则主模型基于任务复杂度给出建议，由用户确认。

### 流程一览

```
快速模式：R1 独立 → R2 交叉验证 → R2.5 30 秒对抗 → 收尾（聊天汇报 + final.md 留痕）
完备模式：R1 独立 → R2 交叉验证 →（R2.5 焦点反驳，可选）→ R3 候选综合
          → R4 对抗挑战 →（R3b 受影响主题回修，最多 1 次）→ 收尾
```

### 三大反模式警示

1. **共识偏见**：多个模型得出相同结论 ≠ 结论正确，可能来自相同训练数据偏见。
2. **确认式终审**：终审只做"我同意"式确认、没有新发现 → 终审形同虚设。
3. **纯抽象讨论**：只在抽象层讨论、不落地到具体场景和操作路径 → 遗漏实际问题。

### 交付目标（所有轮次为此服务）

**用户真正要的，是流程结束后主 Agent 在聊天窗口里用人话讲清的四件事：**

1. **做了什么**：这轮怎么 review 的（几轮、谁参与）
2. **评审结论**：多角度评审的核心发现、共识与分歧
3. **主模型的判断**：综合下来采纳什么、否决什么、为什么
4. **下一步**：接下来做什么

**这段聊天收尾才是主交付**，不是 `final.md`。详见 §收尾。

`final.md` 和过程文档（`r1~r5*.md`）是**留痕档案**——给"想回溯为什么这么决定"的用户、给接手的下游 AI、给未来优化这个流程的人看。它们必须完整、可追溯（保留各轮立场、来源锚点），但用户**不需要**为了拿结论去读它们。

## 前置准备

### Step 1：理解任务 + 任务对齐卡

读懂任务目标、背景、约束。任务可以是：评审已有文档/方案/代码、从零设计方案、探讨问题等。

**任务对齐卡（非阻塞展示，不等确认即进入 Step 2，用户可随时打断调整）**：

```markdown
## 任务对齐
- **目标**：[一句话]
- **关键约束**：[≤ 3 条]
- **成功标准**：[这次 review 最终要回答什么问题]
- **任务类型**：[review | design | discuss | create]
- **模式建议**：[quick | full] — 理由
- **决策模式**：[需确认 | 授权自主] — 见下
- **视角分配**：Claude=... / Codex=...
```

**决策模式（关键字段，决定收尾行为）**：
- **需确认（默认）**：流程跑完，主 Agent 在聊天里汇报结论 + 建议的下一步，**停下等用户拍板**，再执行。
- **授权自主**：用户已表态"你来决定""按结果直接做""不用问我"等 → 流程跑完，主 Agent 直接按评审结论执行下一步任务，完成后回报。

判断依据：用户在发起时是否说了"你决定/直接做/自主"之类。拿不准时默认"需确认"。

**成功标准**会嵌入外部模型的 R1 prompt（见 `references/prompt-templates.md`），让所有模型从第一轮起服务于同一目标。对齐卡保存到 `run-*/task-alignment.md`。

### Step 2：确认参与模型

> **核心原则：模型无关。** 主模型是当前运行本 skill 的模型（Claude），外部模型默认是 Codex。

1. **主模型**：当前模型（Claude），直接参与，无需"调用"。
2. **外部模型**：默认 Codex。检查 `~/.config/cross-review/models.yaml` 是否已配置 `codex`，并跑一次轻量 healthcheck（见 §Preflight）确认 CLI 可用。
3. 如果用户明确点名要再加一个模型（如"也让 GLM 看看"），且该 CLI 已在 `models.yaml` 里配好 `invoke` 模板 → 一并纳入；没配好则告知用户需要先配置，或降级为仅 Claude + Codex。

**models.yaml 最小形态**（只需 codex；加别的 CLI 就照样加一段带 `invoke` 的）：

```yaml
models:
  codex:
    cli_path: /opt/homebrew/bin/codex
    healthcheck: 'codex exec --help >/dev/null 2>&1'
    # codex 是内置：由 cross_review_runtime.py 用 stdin + --output-last-message 调用，无需 invoke 模板
    notes: "OpenAI Codex CLI；走 CLI 默认模型"

  # 可选——接入任意其它 CLI 只需写一行 invoke 模板（{prompt}/{output_file} 占位）：
  # glm:
  #   cli_path: /opt/homebrew/bin/crush
  #   invoke: 'crush run --quiet --model zhipu-coding/glm-5.1 "{prompt}" > {output_file}'
  #   healthcheck: 'crush models >/dev/null 2>&1'
```

> **Codex 内置说明**：`cross_review_runtime.py execute --model codex` 用 `--output-last-message` 只取最终回答（过滤 session 元数据/thinking/命令日志），`--ephemeral` 不留 session 文件。其它 CLI 走各自的 `invoke` 模板。

### Step 3：协作视角分配

主模型按任务类型分配两个主责视角（**主责重点，非唯一视角**——每个模型都应自由报告它发现的任何重要内容）：

| 任务类型 | Claude（主）主责 | Codex（外部）主责 |
|----------|------------------|-------------------|
| 技术类（代码/架构/API） | 架构一致性、数据流、用户体验、替代方案 | 技术实现可行性与风险 |
| 产品/策略类 | 逻辑自洽性、用户影响、替代路径 | 可行性与资源风险 |
| 创作/探讨类 | 结构完整性、核心论点、受众适配 | 差异化视角、反例与边界 |

完备模式的 Round 4，Codex 担任"魔鬼代言人"做对抗攻击，Claude 做综合复核。用户也可直接指定自定义视角。

### Step 4：创建输出目录

在当前工作目录或项目根创建带时间戳的运行目录：

```
cross-review-records/run-{YYYYMMDD-HHmm}/
```

同一任务重跑 → **永远新建 run 目录**（不覆盖历史）。目录名自带时间戳，`ls -t` 即按时间排序，最新的就是最新结论，无需额外的版本链机制。

## 输出契约（所有外部模型调用必须遵守）

发给外部模型的 prompt 末尾必须追加：

```
## 输出格式要求
- 只输出最终分析结果。禁止输出思考过程、命令日志、前言后记。
- 建议使用下方输出骨架，但任务需要时可调整结构。
- 简洁优于冗长，但深度优于简洁。宁可分析透彻写 3000 字，也不要为控制篇幅省略重要发现。
- 请用中文输出。
```

### 输出骨架（评审类）

```markdown
## 结论摘要
[2-3 句概括核心判断]

## 发现
### [Critical|Major|Minor]-1：[标题]
- **证据**：[具体引用位置]
- **影响**：[不修复会怎样]
- **建议**：[具体改法]

## 未决问题
- [不确定但值得关注的点]

## 一句话结论
[整体判断]
```

### 输出骨架（设计/创作类）

```markdown
## 结论摘要
[2-3 句概括方案核心]

## 方案
### 方案要点 1：[标题]
- **内容**：[具体描述]
- **决策理由**：[为什么这样选]

## 替代方案与权衡
## 未决问题
## 一句话结论
```

> Prompt 模板：Read `references/prompt-templates.md` 获取各轮次完整模板。

## 输出验证（每次外部模型返回后）

> **实现**：用 `scripts/cross_review_runtime.py execute` 统一执行外部模型调用。它记录 stdout/stderr/退出码/耗时/重试/校验结果，强制生成 `status.json`、`logs/`、`invalid/`。

**两层校验**（自动）：

- **传输校验**（不通过则失败）：非空且 > 200 字节；不含认证/交互提示词（`Opening authentication`、`Y/n`）；不含 ANSI 噪声；不含 CLI 帮助文本。
- **语义校验**（不通过则标记低质量，但仍纳入流程作为弱信号）：含预期标题（`## 结论摘要`/`## 发现`/`## 方案`）；含至少 1 条发现或方案要点；含 `## 一句话结论`。

**失败处理**：传输校验失败 → 自动重试一次（精简 prompt）→ 再失败则降级（见 §降级）+ 告知用户。无效输出存入 `invalid/`，原始证据存入 `logs/`，不污染主流程。

---

## Preflight（每次 run 启动一次）

用配置里的 `healthcheck` 命令做 CLI 级检查（纯本地，不调模型，< 1 秒）：

| CLI | Healthcheck | 验证 |
|-----|-------------|------|
| Codex | `codex exec --help >/dev/null 2>&1` | CLI + 子命令存在 |
| 其它（如有） | 配置里的 `healthcheck` 字段 | CLI 可执行 |

认证/网络问题由首次正式调用 + 输出校验兜底，不在 preflight 做模型级测试（省时省 token）。Codex 不可用 → 见 §降级。

## 快速模式

### Round 1：独立工作（并行）

1. 主模型直接产出自己视角的结果。
2. 同时用 `cross_review_runtime.py execute` 调用 Codex（后台并行）。
3. 外部模型的 R1 prompt 嵌入 `success_criteria`（从对齐卡带入）。

> Prompt 模板：`references/prompt-templates.md` → "Round 1: Independent Work"

**输出文件**：`r1.claude.md`、`r1.codex.md`。

### Round 2：交叉验证

每个模型读对方的 R1 输出，做验证、质疑、补充（只写增量，禁止复述 R1）。主模型读 Codex 的 clean 输出（已由 `--output-last-message` 去噪）。仅当某 R1 输出 > 5000 字时，主模型制作 digest 再传递。

> Prompt 模板："Round 2: Cross-Validation"

**输出文件**：`r2.claude.md`、`r2.codex.md`。

### Round 2.5：30 秒轻量对抗（防共识偏见）

主模型写完综合草稿后、收尾前，把草稿发给 Codex 用 ≤500 字指出"最致命的 1-2 个攻击点"，主模型据此修订。

> Prompt 模板："Quick Mode: 30-Second Devil's Advocate"

**输出文件**：`r2.attack.codex.md`。

### 收尾

进入 §收尾（聊天汇报 + final.md 留痕）。

## 完备模式

### Round 1-2

与快速模式相同。

### Round 2.5：焦点反驳（可选，仅当有未解决关键冲突时）

触发条件：两个模型在 Critical/Major 问题上持相反意见且均有论据；或某核心决策有多条互斥合理路径。主模型列出 1-3 个冲突点，构造聚焦 prompt 让模型只回应该冲突点。

**输出文件**：`r2.5.codex.md`。

### Round 3：候选综合（主模型主导）

主模型读全部 R1+R2(+R2.5)，按主题聚类综合，提出**候选方案**（措辞用"候选/建议/待验证"，不用"最终/最优"），并为每个方案列出"待检验的假设"和"未解冲突"。

> 文档结构：`references/prompt-templates.md` → "Round 3: Candidate Synthesis Structure"

**输出文件**：`r3.synthesis.md`。

### Round 4：对抗性挑战（核心轮）

前三轮是"完成任务"，Round 4 是"攻击我们自己的成果"。

1. Read `references/round4-attack-checklist.md` 获取四项强制检查。
2. **Codex 担任魔鬼代言人**深入全部四项检查（同类问题回环检测、具体场景走查、"去掉它试试"测试、共识盲点检测）；**主模型独立做全部四项 + 综合复核**。
3. 并行执行。

> Prompt 模板："Round 4: Focused Attack"

**输出文件**：`r4.claude.md`、`r4.codex.md`。

**回路机制**：发现 Critical → 回到 Round 3b（只重跑受影响主题），产出 `r3b.synthesis.md`，再重新进入 Round 4；发现 Major → 记为遗留风险，评估是否回路。**回路最多 1 次**。

### Round 5：综合 + 可选独立复核

1. 主模型整合 R4 对抗结果，形成最终结论。
2. **可选独立复核**：把最终结论发给 Codex，问"这个结论站得住吗？有没有被边缘化的少数意见或遗漏的盲点？"（对抗"确认式终审"反模式）。如指出关键问题 → 主模型修订。
3. 进入 §收尾。

**输出文件**：`r5.review.codex.md`（如做复核）。

## 收尾（核心交付）

> 这是整个流程的终点和主交付。不管哪种模式，跑完都必须执行。

### 第一步：聊天窗口汇报（必做）

主 Agent 在**聊天窗口**用人话输出收尾汇报，四段，**禁止轮次代号/模型黑话/方法论术语**（不要出现 "R4 Critical-1""r3b.synthesis""魔鬼代言人""价值主张校正"这类）：

```markdown
**做了什么**：[一两句——几轮、谁参与、怎么 review 的]

**评审结论**：[多角度评审的核心发现；有共识说共识，有分歧说分歧]

**我的判断**：[综合下来采纳什么、否决什么、为什么；这是主模型自己的立场]

**下一步**：[接下来具体做什么]
```

要求：说人话、聚焦"决定 + 行动"、把最关键的诚实话（这个方案能做到什么、做不到什么）放在前面。

### 第二步：按决策模式行动

- **需确认（默认）**：汇报后**停下**，等用户拍板（确认 / 调整 / 否决），再执行下一步。
- **授权自主**：不停，**直接按"下一步"执行任务**（改代码、写文档、调用其它 skill 等），完成后回报结果与验证情况。

### 第三步：落地 final.md 留痕（必做，但不展示给用户读）

按 `templates/final.md.tmpl` 生成 `final.md` 存档（见 §final.md）。生成后**不需要**要求用户去读它——只在收尾汇报里附一句"完整记录在 `run-xxx/final.md`，想回溯随时查"即可。

可选自检：`python3 scripts/cross_review_runtime.py check-final --file <path>`（校验 frontmatter）。

## final.md（留痕档案）

**定位**：留痕档案，给"想回溯的用户 / 下游 AI / 未来优化流程的人"。不是用户拿结论的主路径（那是聊天收尾）。但正因为它是未来审计和优化的依据，**必须完整、精确、可追溯**——保留各轮立场、来源锚点、模型归属。

### 模板

`templates/final.md.tmpl` — 所有任务类型共用。

### 内部分层（关键）

1. **顶部 `## 给你`**：聊天收尾那段话的存档——人话结论，零代号。用户偶尔打开 final.md，看这一块就够，不必往下钻。
2. **正文 §1-§7**：完整的过程留痕——任务约束、核心分歧与裁决（保留各方立场 + 来源锚点如"来源：R4 修正#1"）、最终方案、被否决路径、行动项、遗留风险、讨论脉络。代号、轮次、模型名在这一层**保留**（审计和下游 AI 恰恰需要这些精确信息）。

### frontmatter：闭集，禁止塞叙事

frontmatter 是给机器（`check-final`、下游解析）的元数据，**只允许 12 个字段**，多出来的（如 `review_notes`、`unavailable`）一律不许加——过程记录（修订史、偏差自省）属于正文溯源区或 `r*.md`，不进 frontmatter：

- **必填 8**：`task`（标题级一句，非长哲学）、`mode`、`task_type`、`models`（只列实际产出的模型）、`run_id`、`created_at`、`status`、`success_criteria`（单行摘要，明细下沉 §1）
- **可选 4**：`supersedes`、`superseded_by`、`synthesis_bias_note`（≤1 句，默认 null）、`independent_review`

### 校验

`check-final` 只校验 **frontmatter**（必填字段齐全 + 闭集无多余字段 + `task_type` 合法 + 总行数 ≤ 800）——用 YAML 解析，不碰正文。正文的结构（有没有 `## 给你`、决策有没有写清"做什么/为什么/来源"）由主模型按模板自检保证，不靠脆弱的正文正则。

### action.md（可选）

行动项很多（P0+P1+P2 ≥ 3 条）时，可拆出 `action.md`（见 `templates/action.md.tmpl`）；否则全部内嵌 final.md §5。

## 降级策略

| 可用模型 | 策略 |
|----------|------|
| Claude + Codex（正常） | 各担主责视角；完备模式 Codex 做魔鬼代言人 |
| 仅 Claude（Codex 不可用） | 主模型在不同轮次/prompt 中切换视角自我对抗；收尾时**明确告知用户"本次 Codex 未跑通，仅单模型，结论可信度打折"** |

Codex 调用失败（重试后仍失败）→ 不中止整个 run，降级为单模型，并在聊天收尾 + final.md 的 `models` 字段如实反映（只列实际产出的模型，不掩饰）。
